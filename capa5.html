    Capas 5, 6 y 7

    Sesión, presentación y aplicación

    En el modelo TCP/IP estas tres capas OSI se funden en una sola: la capa de aplicación. Aquí los programas se ponen de acuerdo en qué se dicen (HTTP, DNS, SSH), cómo se codifica (texto, JSON, compresión, cifrado) y cuánto dura la conversación (sesiones).

    Capa OSIResponsabilidadEjemplos que veremos
    7 AplicaciónEl "idioma" del servicioHTTP, DNS, SSH
    6 PresentaciónFormato, codificación, compresión, cifradoUTF-8, Base64, gzip, JSON, TLS
    5 SesiónAbrir, mantener y retomar conversacionesCookies, keep-alive, reanudación TLS, sesiones SSH

    5.1 Laboratorio base

    Un cliente (pc1) y un servidor (pc2). Además le damos a pc1 un fichero hosts propio para poder usar el nombre servidor.lab.

    host
    $ sudo ip netns add pc1
$ sudo ip netns add pc2
$ sudo ip link add eth0 netns pc1 type veth peer name eth0 netns pc2
$ sudo mkdir -p /etc/netns/pc1
$ echo "10.0.0.2 servidor.lab" | sudo tee /etc/netns/pc1/hosts
    pc1 / pc2
    pc1# ip link set lo up
pc1# ip link set eth0 up
pc1# ip addr add 10.0.0.1/24 dev eth0
pc2# ip link set lo up
pc2# ip link set eth0 up
pc2# ip addr add 10.0.0.2/24 dev eth0

    ip netns exec monta cada fichero de /etc/netns/pc1/ encima del de /etc solo para ese namespace. Así pc1 tiene su propio /etc/hosts sin tocar el tuyo. Entra en pc1 después de crear el fichero: sudo ip netns exec pc1 bash y prueba getent hosts servidor.lab.

    5.3 Sesiones: cookies y conexiones persistentes

    HTTP no tiene memoria: cada petición es independiente. Para "recordar" a un usuario (sesión iniciada, carrito) el servidor entrega una cookie y el cliente la devuelve en cada petición.

    pc1 (con el nc -C -l 80 de pc2 contestando con Set-Cookie)
    # -c guarda las cookies recibidas en un fichero ("tarro de cookies")
pc1# curl -c /tmp/lab-cookies.txt http://servidor.lab/
pc1# cat /tmp/lab-cookies.txt
# -b las envía en la siguiente petición: mira en pc2 la cabecera "Cookie:"
pc1# curl -b /tmp/lab-cookies.txt http://servidor.lab/perfil

    Quien copie la cookie de sesión es el usuario para el servidor. Por eso las cookies de sesión se marcan HttpOnly (JavaScript no puede leerlas) y Secure (solo viajan por HTTPS).

    Una conexión, varias peticiones (keep-alive)

    Abrir una conexión TCP cuesta un handshake. HTTP/1.1 reutiliza la misma conexión para varias peticiones. Vuelve a lanzar python -m http.server 80 --directory /tmp/lab-http --protocol HTTP/1.1 en pc2:

    pc2 y pc1
    pc2# tcpdump -i eth0 -n 'tcp[tcpflags] & (tcp-syn|tcp-fin) != 0'
pc1# curl -v http://servidor.lab/ http://servidor.lab/index.html

    curl dice Re-using existing connection y tcpdump muestra un solo SYN para las dos peticiones. En HTTP/2 y HTTP/3 se va más allá: muchas peticiones simultáneas en la misma conexión (multiplexación).

    5.4 Presentación: codificar no es cifrar

    pc1
    # Texto → bytes: UTF-8 usa 2 bytes para la "ñ"
pc1# echo -n "año" | xxd
# Base64: convierte bytes en texto imprimible
pc1# echo -n "ana:secreto" | base64
pc1# echo "YW5hOnNlY3JldG8=" | base64 -d
# Compresión gzip
pc1# echo "hola hola hola hola hola hola hola hola" | gzip | xxd

    Ahora mira cómo viaja una contraseña con autenticación HTTP Basic (con el nc -C -l 80 de pc2 escuchando):

    pc1
    pc1# curl -u ana:secreto http://servidor.lab/privado
    GET /privado HTTP/1.1
Host: servidor.lab
Authorization: Basic YW5hOnNlY3JldG8=
User-Agent: curl/8.x

    Cualquiera que capture el tráfico la decodifica con base64 -d. Base64 es presentación (formato), no seguridad. Para eso está TLS.

    TécnicaPropósito¿Reversible sin clave?
    UTF-8, ASCIIRepresentar texto como bytesSí
    Base64, URL-encodingTransportar bytes por canales de textoSí
    gzip, brotliOcupar menosSí
    JSON, XML, ProtobufEstructurar datosSí
    Hash (SHA-256)Huella / integridadNo (unidireccional)
    Cifrado (AES, ChaCha20)ConfidencialidadNo

    5.5 TLS: HTTPS con tu propio certificado

    Crear un certificado autofirmado

    host
    $ mkdir -p /tmp/lab-tls
$ cd /tmp/lab-tls
$ openssl req -x509 -newkey ed25519 -nodes -days 7 -keyout servidor.key -out servidor.crt -subj "/CN=servidor.lab" -addext "subjectAltName=DNS:servidor.lab"
# Ver lo que contiene
$ openssl x509 -in servidor.crt -noout -text

    Servidor TLS y cliente

    pc2
    # -www: responde con una página de estado de la sesión TLS
pc2# openssl s_server -accept 443 -cert /tmp/lab-tls/servidor.crt -key /tmp/lab-tls/servidor.key -www
    pc1
    # Cliente TLS de diagnóstico: muestra certificado, versión y cifrado negociado
pc1# openssl s_client -connect servidor.lab:443 -servername servidor.lab -CAfile /tmp/lab-tls/servidor.crt
# curl sin indicarle el certificado: falla (no confía en él)
pc1# curl https://servidor.lab/
# curl confiando en nuestro certificado
pc1# curl --cacert /tmp/lab-tls/servidor.crt https://servidor.lab/

    Qué ve un espía

    pc2
    pc2# tcpdump -i eth0 -n -A port 443

    Repite el curl --cacert …. Busca en la salida servidor.lab: aparece en el ClientHello (la extensión SNI viaja en claro para que el servidor sepa qué certificado mostrar). Todo lo demás —ruta, cabeceras, cookies, contenido— es ilegible. Compáralo con el mismo tcpdump -A sobre el puerto 80.

    PropiedadCómo la consigue TLS
    ConfidencialidadCifrado simétrico (AES-GCM, ChaCha20) con claves de sesión
    IntegridadCifrado autenticado (AEAD): cualquier cambio se detecta
    Autenticación del servidorCertificado firmado por una CA en la que el cliente confía
    Secreto hacia delanteClaves efímeras (ECDHE): robar la clave del servidor después no descifra lo grabado antes
    Reanudación de sesión (capa 5)Tickets/PSK: reconectar sin repetir todo el handshake
    Extra: tu propia autoridad de certificación (CA)
    host · /tmp/lab-tls
    # La CA
$ openssl req -x509 -newkey ed25519 -nodes -days 30 -keyout ca.key -out ca.crt -subj "/CN=CA del laboratorio"
# Petición de firma (CSR) del servidor
$ openssl req -newkey ed25519 -nodes -keyout web.key -out web.csr -subj "/CN=servidor.lab"
# La CA firma la petición
$ openssl x509 -req -in web.csr -CA ca.crt -CAkey ca.key -CAcreateserial -days 7 -out web.crt -extfile <(echo "subjectAltName=DNS:servidor.lab")
# Verificar la cadena
$ openssl verify -CAfile ca.crt web.crt

    Arranca s_server con web.crt/web.key y en el cliente usa --cacert ca.crt: confías en la CA y, por tanto, en todo lo que firme. Así funciona la web real (con CAs como Let's Encrypt preinstaladas en tu sistema).

    5.6 DNS por dentro

    Ponemos en pc2 un DNS con varios tipos de registro:

    pc2
    pc2# dnsmasq --no-daemon --interface=eth0 --bind-interfaces --no-resolv --no-hosts --pid-file= --log-queries --host-record=servidor.lab,10.0.0.2 --cname=www.lab,servidor.lab --mx-host=lab,correo.lab,10 --host-record=correo.lab,10.0.0.25 --txt-record=lab,"v=spf1 mx -all" --srv-host=_ldap._tcp.lab,servidor.lab,389
    pc1
    pc1# dig @10.0.0.2 servidor.lab A
pc1# dig @10.0.0.2 www.lab
pc1# dig @10.0.0.2 lab MX
pc1# dig @10.0.0.2 lab TXT
pc1# dig @10.0.0.2 _ldap._tcp.lab SRV
pc1# dig @10.0.0.2 -x 10.0.0.2
# Forzar TCP en lugar de UDP
pc1# dig @10.0.0.2 servidor.lab +tcp
    RegistroContieneEjemplo
    A / AAAAIPv4 / IPv6servidor.lab → 10.0.0.2
    CNAMEAlias de otro nombrewww.lab → servidor.lab
    MXServidor de correo del dominio, con prioridadlab → 10 correo.lab
    TXTTexto libre (SPF, verificaciones)"v=spf1 mx -all"
    SRVDónde está un servicio (host + puerto)_ldap._tcp.lab → servidor.lab:389 (Active Directory los usa mucho)
    PTRResolución inversa2.0.0.10.in-addr.arpa → servidor.lab
    NS / SOAServidores con autoridad sobre la zona / datos de la zona—

    Una consulta DNS fabricada con scapy

    scapy en pc1
    >>> q = IP(dst="10.0.0.2") / UDP(sport=33000, dport=53) / DNS(id=0xbeef, rd=1, qd=DNSQR(qname="servidor.lab", qtype="A"))
>>> q.show()
>>> r = sr1(q, timeout=2)
>>> r[DNS].id, r[DNS].rcode, r[DNS].an.rdata
    (48879, 0, '10.0.0.2')

    El id de la respuesta coincide con el de la pregunta: así el cliente empareja respuestas. rcode 0 = sin error, 3 = NXDOMAIN (no existe).

    5.7 SSH: sesiones remotas y túneles

    SSH reúne las tres capas: autentica, cifra y mantiene una sesión interactiva (y puede transportar otras conexiones dentro). Arranca un servidor en pc2 (si nunca has usado sshd, genera antes las claves de host con sudo ssh-keygen -A):

    pc2
    pc2# /usr/bin/sshd -D -p 22 -o PidFile=none
    host → pc1 como tu usuario
    $ sudo ip netns exec pc1 sudo -u $USER ssh $USER@10.0.0.2

    (Entras con tu propia contraseña: es el mismo sistema, solo que a través de la red del laboratorio. Ejecuta ip -br addr dentro: verás la red de pc2.)

    TúnelOpciónQué haceEjemplo
    Local-LUn puerto de tu equipo lleva a un destino visto desde el servidorssh -L 8080:127.0.0.1:80 usuario@10.0.0.2 → curl localhost:8080
    Remoto-RUn puerto del servidor lleva a un destino visto desde tissh -R 9000:127.0.0.1:22 usuario@10.0.0.2
    Dinámico (SOCKS)-DProxy SOCKS: cualquier destino, salida por el servidorssh -D 1080 usuario@10.0.0.2 → curl --socks5 localhost:1080 http://…
    Saltos-JAtravesar equipos intermediosVer la red tipo onion

    La autenticación por claves y el control de quién puede entrar se ven en Permisos e identidad.

    5.8 Una petición atravesando todas las capas

    Con el servidor HTTP de pc2 en marcha, captura en pc1 a fichero y haz una sola petición:

    pc1
    pc1# ip neigh flush dev eth0
pc1# tcpdump -i eth0 -n -e -w /tmp/lab-todo.pcap &
pc1# curl http://servidor.lab/
pc1# kill %1
pc1# tcpdump -n -e -r /tmp/lab-todo.pcap
    #PaquetesCapaQué está pasando
    1— (lectura de /etc/hosts)7Nombre → IP. Con DNS verías aquí una consulta UDP 53
    2ARP request / reply2IP → MAC del servidor (o del router)
    3SYN, SYN-ACK, ACK4Abrir la conexión TCP
    4PSH-ACK con GET /7La petición HTTP
    5ACK + respuesta 200 OK4 / 7Confirmación y contenido
    6FIN, ACK…4Cierre

    Abre /tmp/lab-todo.pcap con Wireshark (sudo pacman -S wireshark-qt) y despliega cada paquete: verás Ethernet → IP → TCP → HTTP, exactamente la encapsulación de la portada.
