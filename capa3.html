    Capa 3 · Red

    Capa 3: IP, routers y servicios de red

    La capa de red lleva paquetes de una red a otra. La MAC solo sirve dentro de un segmento; la IP identifica al equipo de punta a punta y los routers deciden el siguiente salto.

    Convención de esta página. Los cables (pares veth) se crean desde el host. Para configurar cada aparato abre una terminal dentro de él:

    host
    $ sudo ip netns exec r1 bash

    Los bloques etiquetados r1, pc1… se escriben en esa terminal, sin sudo ip netns exec delante. El prompt r1# te recuerda dónde estás. Si prefieres no abrir terminales, añade sudo ip netns exec r1 delante de cada comando: es equivalente.

RTNETLINK answers: Network is unreachable

    Al poner la IP con /24, el kernel añade solo una ruta conectada: "toda la 10.0.0.0/24 está directamente en eth0". Para cualquier otra red no hay ruta: Network is unreachable. Para salir de su red, un PC necesita un router y una puerta de enlace.

    Parte de la rutaSignificado
    10.0.0.0/24Destino (red)
    dev eth0Interfaz de salida
    via XSiguiente salto (router). Si no aparece, el destino está en la misma red
    proto kernelQuién la creó: kernel (automática), static (a mano), dhcp, bird…
    scope linkDestino alcanzable directamente en el enlace
    src 10.0.0.1IP de origen preferida
    metric NPrioridad: menor = preferida

    Con un switch en medio la capa 3 no cambia nada: los PCs siguen en la misma red 10.0.0.0/24 y no necesitan router. Repite el laboratorio 2.6 si quieres verlo: el switch es transparente para IP.

    3.3 Un router entre dos redes

    Crear aparatos y cables

    host

    Configurar el router

    r1
    r1# ip link set lo up
r1# ip link set eth1 up
r1# ip link set eth2 up
r1# ip addr add 10.0.1.1/24 dev eth1
r1# ip addr add 10.0.2.1/24 dev eth2
# Lo que convierte un equipo en router: reenviar paquetes que no son para él
r1# sysctl -w net.ipv4.ip_forward=1
r1# ip route

    Configurar los PCs con su puerta de enlace

    pc1
    pc1# ip link set lo up
pc1# ip link set eth0 up
pc1# ip addr add 10.0.1.10/24 dev eth0
# Ruta por defecto: "para todo lo que no conozca, pregunta al router"
pc1# ip route add default via 10.0.1.1
    pc2
    pc2# ip link set lo up
pc2# ip link set eth0 up
pc2# ip addr add 10.0.2.10/24 dev eth0
pc2# ip route add default via 10.0.2.1
    pc1
    pc1# ping -c 3 10.0.2.10
pc1# ip route get 10.0.2.10

    Qué cambia y qué no al atravesar un router

    Captura a los dos lados del router a la vez (dos terminales):

    r1 · terminal A y B
    r1# tcpdump -i eth1 -e -n -v icmp
r1# tcpdump -i eth2 -e -n -v icmp

    Experimentos

    r1 y pc1
    # 1) Apaga el reenvío: los pings se pierden en silencio
r1# sysctl -w net.ipv4.ip_forward=0
pc1# ping -c 2 10.0.2.10
r1# sysctl -w net.ipv4.ip_forward=1
# 2) Quita la puerta de enlace de pc2: pc1 envía, pero pc2 no sabe responder
pc2# ip route del default
pc1# ping -c 2 10.0.2.10
pc2# ip route add default via 10.0.2.1
# 3) Un equipo que no existe en la red 2: r1 responde "Destination Host Unreachable"
pc1# ping -c 2 10.0.2.99
# 4) Un ping con TTL=1: muere en r1, que avisa con "Time to live exceeded"
pc1# ping -c 1 -t 1 10.0.2.10
# 5) La tabla ARP de pc1 NO contiene a pc2, sino al router
pc1# ip neigh

    Regla de oro: para un destino de otra red, la trama va a la MAC del router pero el paquete lleva la IP del destino final.

    Enrutamiento dinámico con OSPF (BIRD)

    Con OSPF los routers se descubren, intercambian sus redes y recalculan caminos solos. Arch trae bird en los repositorios oficiales: sudo pacman -S bird. Primero borra las rutas estáticas de los tres routers (las rutas puestas a mano con ip route add llevan proto boot), o recrea el laboratorio sin el paso de rutas.

    r1 (repite en r2 y r3)
    r1# ip route flush proto boot

    Crea un fichero de configuración por router, por ejemplo /etc/bird-r1.conf (en r2 y r3 cambia solo el router id):

    /etc/bird-r1.conf
    router id 1.1.1.1;

protocol device { }

protocol kernel {
  ipv4 { export all; };
}

protocol ospf v2 {
  ipv4 { import all; };
  area 0 {
    interface "to-*" { type ptp; cost 10; hello 2; dead 8; };
    interface "lan" { stub yes; };
  };
}
    r1, r2, r3 (cada uno con su fichero y su socket)
    r1# bird -c /etc/bird-r1.conf -s /run/bird-r1.ctl
r2# bird -c /etc/bird-r2.conf -s /run/bird-r2.ctl
r3# bird -c /etc/bird-r3.conf -s /run/bird-r3.ctl
# Consultar vecinos y rutas aprendidas
r1# birdc -s /run/bird-r1.ctl show ospf neighbors
r1# birdc -s /run/bird-r1.ctl show route
r1# ip route show proto bird

    Repite el experimento de cortar r1–r2: en unos segundos (dead 8) OSPF reconverge y el tráfico va por r3. Para parar BIRD: birdc -s /run/bird-r1.ctl down.

    Fragmentación

    r2 y pc1
    # Reducimos la MTU del enlace r2–r3 a 600 bytes
r2# ip link set eth2 mtu 600
r3# ip link set eth1 mtu 600
# Mirar el enlace estrecho
r3# tcpdump -i eth1 -n -v icmp
# Ping grande que permite fragmentar: r2 lo trocea
pc1# ping -c 1 -s 1400 -M dont 10.0.2.10
# Ping grande con DF (no fragmentar): r2 devuelve "Frag needed and DF set (mtu = 600)"
pc1# ping -c 1 -s 1400 -M do 10.0.2.10

    En tcpdump verás flags [+] (más fragmentos), offset y el mismo id en todos los trozos. Con scapy puedes fragmentar tú: send(fragment(IP(dst="10.0.2.10")/ICMP()/(b"X"*1400), fragsize=500)).

    3.7 Una LAN con servidores: DHCP, DNS y web

    Montamos una oficina: un switch, un servidor srv que da DHCP, DNS y web, y dos clientes que se configuran solos.

    host

    3.8 NAT: una red privada saliendo a "Internet"

    Las IPs privadas no se enrutan por Internet. El router de casa hace NAT: cambia la IP de origen privada por su IP pública al salir, y deshace el cambio en las respuestas.

    host
    $ sudo ip netns add casa
$ sudo ip netns add gw
$ sudo ip netns add internet
$ sudo ip link add eth0 netns casa type veth peer name lan netns gw
$ sudo ip link add wan netns gw type veth peer name eth0 netns internet
    casa
    casa# ip link set lo up
casa# ip link set eth0 up
casa# ip addr add 192.168.1.10/24 dev eth0
casa# ip route add default via 192.168.1.1
    internet
    # OJO: "internet" NO tiene ruta hacia 192.168.1.0/24, como en la vida real
internet# ip link set lo up
internet# ip link set eth0 up
internet# ip addr add 203.0.113.1/24 dev eth0
    gw
    gw# ip link set lo up
gw# ip link set lan up
gw# ip link set wan up
gw# ip addr add 192.168.1.1/24 dev lan
gw# ip addr add 203.0.113.2/24 dev wan
gw# ip route add default via 203.0.113.1
gw# sysctl -w net.ipv4.ip_forward=1
    probar sin NAT
    internet# tcpdump -i eth0 -n icmp
casa# ping -c 2 203.0.113.1

    Internet recibe los pings desde 192.168.1.10, pero no sabe cómo volver a esa red privada: no hay respuesta. Activamos NAT:

    gw
    # Todo lo que salga por wan: cambia la IP origen por la de wan
gw# iptables -t nat -A POSTROUTING -o wan -j MASQUERADE
gw# iptables -t nat -L -n -v
    probar con NAT
    casa# ping -c 2 203.0.113.1
# La tabla de traducciones (connection tracking)
gw# conntrack -L
    icmp     1 29 src=192.168.1.10 dst=203.0.113.1 type=8 code=0 id=7 src=203.0.113.1 dst=203.0.113.2 type=0 code=0 id=7 mark=0 use=1

    Cada línea de conntrack tiene dos mitades: el sentido original (lo que envió casa) y el sentido de respuesta esperado (lo que contestará internet, a la IP pública). Así gw sabe a quién devolver cada respuesta.

    DNAT: abrir un puerto (port forwarding)

    Al revés: que desde Internet se pueda llegar a un servicio de casa.

    casa, gw, internet
    # Servidor web en casa
casa# python -m http.server 8000
# En gw: lo que llegue al puerto 80 de wan → casa:8000
gw# iptables -t nat -A PREROUTING -i wan -p tcp --dport 80 -j DNAT --to-destination 192.168.1.10:8000
# Desde internet se accede a la IP pública del router
internet# curl http://203.0.113.2/
    TipoCadenaQué cambiaEjemplo real
    SNAT / MASQUERADEPOSTROUTINGIP (y puerto) de origenRouter de casa, CGNAT
    DNATPREROUTINGIP (y puerto) de destinoAbrir puertos, balanceadores
    REDIRECTPREROUTING / OUTPUTDestino → el propio equipoProxy transparente
    host · limpieza
    $ sudo ip netns del casa
$ sudo ip netns del gw
$ sudo ip netns del internet
    Extra: dar Internet real a un namespace

    Esto sí toca tu host (activa el reenvío y añade una regla NAT), por eso está aparte. Sustituye wlan0 por tu interfaz real (míralo con ip route get 1.1.1.1).

    host
    $ sudo ip netns add salida
$ sudo ip link add veth-host type veth peer name eth0 netns salida
$ sudo ip addr add 172.31.0.1/30 dev veth-host
$ sudo ip link set veth-host up
$ sudo ip netns exec salida ip addr add 172.31.0.2/30 dev eth0
$ sudo ip netns exec salida ip link set eth0 up
$ sudo ip netns exec salida ip route add default via 172.31.0.1
$ sudo sysctl -w net.ipv4.ip_forward=1
$ sudo iptables -t nat -A POSTROUTING -s 172.31.0.0/30 -o wlan0 -j MASQUERADE
$ sudo mkdir -p /etc/netns/salida
$ echo "nameserver 1.1.1.1" | sudo tee /etc/netns/salida/resolv.conf
$ sudo ip netns exec salida curl -I https://archlinux.org

    Si tienes un cortafuegos en el host (ufw, firewalld, nftables con política DROP en FORWARD) quizá debas permitir el reenvío. Para deshacerlo:

    host · deshacer
    $ sudo iptables -t nat -D POSTROUTING -s 172.31.0.0/30 -o wlan0 -j MASQUERADE
$ sudo sysctl -w net.ipv4.ip_forward=0
$ sudo ip netns del salida
$ sudo rm -r /etc/netns/salida

# 6. La LAN puede ir a la web de pc2

    3.11 VPN con WireGuard

    Una VPN crea un túnel cifrado: una interfaz virtual (wg0) cuyos paquetes se meten, cifrados, dentro de paquetes UDP normales. Usamos el laboratorio 3.3: pc1 y pc2 se hablarán por el túnel y r1 solo verá UDP cifrado. Si dejaste puesto el cortafuegos de 3.9, permite el túnel en r1: iptables -I FORWARD 1 -p udp --dport 51820 -j ACCEPT.

    1. Claves (una pareja privada/pública por extremo)

    host
    $ mkdir -p /tmp/lab-wg
$ cd /tmp/lab-wg
$ umask 077
$ wg genkey > pc1.key
$ wg pubkey < pc1.key > pc1.pub
$ wg genkey > pc2.key
$ wg pubkey < pc2.key > pc2.pub
$ cat pc1.pub
$ cat pc2.pub

    2. Interfaz WireGuard en pc1

    pc1

pc1# wg set wg0 private-key /tmp/lab-wg/pc1.key listen-port 51820
# Sustituye CLAVE_PUBLICA_PC2 por el contenido de pc2.pub
pc1# wg set wg0 peer CLAVE_PUBLICA_PC2 endpoint 10.0.2.10:51820 allowed-ips 10.99.0.2/32
pc1# ip addr add 10.99.0.1/24 dev wg0
pc1# ip link set wg0 up

    3. Interfaz WireGuard en pc2

    pc2
    pc2# ip link add wg0 type wireguard
pc2# wg set wg0 private-key /tmp/lab-wg/pc2.key listen-port 51820
pc2# wg set wg0 peer CLAVE_PUBLICA_PC1 endpoint 10.0.1.10:51820 allowed-ips 10.99.0.1/32
pc2# ip addr add 10.99.0.2/24 dev wg0
pc2# ip link set wg0 up

    4. Probar y observar

    r1, pc2 y pc1

    IdentidadClave pública de cada extremo (como las claves SSH)
    endpointIP:puerto real donde está el otro extremo
    allowed-ipsQué IPs internas se aceptan de ese peer y qué destinos se le envían (a la vez filtro y tabla de rutas)

    3.12 Una red de relevos tipo onion (concepto de Tor)

    socat acepta conexiones en un puerto y las reenvía a otro equipo. Encadenamos tres:

    n3, n2, n1 (cada uno en su terminal)

    El cliente recibe la página. Mira los mensajes de cada socat (con -d -d imprime quién se conecta) y el log del servidor web: el servidor cree que le habla 10.50.0.3. Problema: espía en n1 y verás todo en claro:

    n1
    n1# tcpdump -i eth0 -n -A port 9001

    n1 lee "contenido secreto del servidor". Sin cifrado, un relevo malicioso lo ve todo. Para (Ctrl+C) los socat.

    Parte B: cifrado en capas con saltos SSH anidados

    SSH con -J (ProxyJump) hace algo muy parecido a un circuito onion: el cliente abre una sesión cifrada con n1; dentro de ella abre otra con n2; y dentro de esa, otra con n3. Cada relevo solo puede quitar su propia capa.

    Prepara un servidor SSH en cada relevo (necesita el paquete openssh y las claves de host del sistema; si nunca has usado sshd, genera las claves de host con sudo ssh-keygen -A):

    host · una clave para tu usuario
    $ ssh-keygen -t ed25519 -f ~/.ssh/lab_onion -N ""
$ cat ~/.ssh/lab_onion.pub >> ~/.ssh/authorized_keys
$ chmod 600 ~/.ssh/authorized_keys
    n1, n2, n3 (cada uno en su terminal; sshd en primer plano con -D)
    n1# /usr/bin/sshd -D -p 2222 -o PasswordAuthentication=no -o PidFile=none
n2# /usr/bin/sshd -D -p 2222 -o PasswordAuthentication=no -o PidFile=none
n3# /usr/bin/sshd -D -p 2222 -o PasswordAuthentication=no -o PidFile=none

    Desde el cliente, como tu usuario normal (no root), construimos el circuito y abrimos un túnel: el puerto local 8080 sale por n3 hacia el servidor web.

    host → cliente como tu usuario
    $ sudo ip netns exec cliente sudo -u $USER ssh -i ~/.ssh/lab_onion -o StrictHostKeyChecking=accept-new -J $USER@10.50.0.1:2222,$USER@10.50.0.2:2222 -p 2222 -N -L 8080:10.50.0.100:80 $USER@10.50.0.3
    cliente (otra terminal) y n1
    n1# tcpdump -i eth0 -n -A port 2222
cliente# curl http://127.0.0.1:8080/

    Ahora en n1 solo verás bytes ilegibles; el texto ya no aparece. Comprueba con tcpdump en cada relevo con quién habla cada uno:

Este laboratorio solo ilustra la idea central: enrutamiento por relevos + cifrado en capas. Fíjate también en la lección de la última fila: el nodo de salida ve el tráfico si la aplicación no lo cifra, por eso HTTPS sigue siendo necesario.

    3.13 IPv6 en dos minutos

    IPv6 viene activado en cada namespace. Al encender una interfaz, se autoasigna una dirección link-local (fe80::/64) derivada de la MAC. En lugar de ARP usa NDP (mensajes ICMPv6).

    con el laboratorio 3.2 (pc1 y pc2 directos)
    pc1# ip -6 addr show eth0
pc1# ip addr add 2001:db8::1/64 dev eth0
pc2# ip addr add 2001:db8::2/64 dev eth0
pc2# tcpdump -i eth0 -n icmp6
pc1# ping -c 2 2001:db8::2
# La "tabla ARP" de IPv6
pc1# ip -6 neigh
# Ping a todos los equipos del enlace (multicast ff02::1)
pc1# ping -c 2 -I eth0 ff02::1

    3.14 Enrutamiento por políticas (avanzado)

    Normalmente la ruta depende solo del destino. Con ip rule puede depender del origen, de una marca del cortafuegos, etc. Ejemplo en un router con dos salidas (wan1, wan2): los equipos 10.0.1.0/25 salen por wan2.

    router con dos salidas
    r# ip route add default via 198.51.100.1 table 100
r# ip rule add from 10.0.1.0/25 table 100 priority 1000
r# ip rule show
r# ip route show table 100
# Comprobar qué ruta usaría un paquete desde un origen concreto
r# ip route get 8.8.8.8 from 10.0.1.5 iif lan
