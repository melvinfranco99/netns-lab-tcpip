    Capa 4: puertos, UDP y TCP

    IP lleva paquetes de un equipo a otro. La capa de transporte los lleva de un programa a otro, usando puertos. TCP además garantiza que llega todo, en orden y sin duplicados; UDP no garantiza nada pero es rápido y simple.

    4.1 Laboratorio base

    Dos PCs unidos directamente, como en la capa 3. Abre una terminal en cada uno con sudo ip netns exec pcN bash.

    host
    $ sudo ip netns add pc1
$ sudo ip netns add pc2
$ sudo ip link add eth0 netns pc1 type veth peer name eth0 netns pc2
    pc1 / pc2
    pc1# ip link set lo up
pc1# ip link set eth0 up
pc1# ip addr add 10.0.0.1/24 dev eth0
pc2# ip link set lo up
pc2# ip link set eth0 up
pc2# ip addr add 10.0.0.2/24 dev eth0

    4.2 Puertos y sockets

    Una conexión queda identificada por 5 datos: protocolo, IP origen, puerto origen, IP destino, puerto destino. Por eso un servidor web puede tener miles de clientes en el mismo puerto 80: cada uno usa un puerto origen distinto.

    RangoNombreUso
    0 – 1023Bien conocidosServicios estándar; solo root (o CAP_NET_BIND_SERVICE) puede escucharlos
    1024 – 49151RegistradosAplicaciones (3306 MySQL, 5432 PostgreSQL, 8080…)
    32768 – 60999Efímeros (Linux)Puerto origen aleatorio del cliente. Ver sysctl net.ipv4.ip_local_port_range
    PuertoProtoServicioPuertoProtoServicio
    22TCPSSH53UDP/TCPDNS
    25TCPSMTP67/68UDPDHCP servidor/cliente

    Ver quién escucha: ss

    pc2
    # Abrimos un servidor TCP y uno UDP
pc2# nc -lk 5000 &
pc2# nc -luk 6000 &
# -t TCP, -u UDP, -l escuchando, -p proceso, -n numérico
pc2# ss -tulpn
    Netid State  Recv-Q Send-Q Local Address:Port Peer Address:Port Process
udp   UNCONN 0      0            0.0.0.0:6000      0.0.0.0:*     users:(("nc",pid=812,fd=3))
tcp   LISTEN 0      1            0.0.0.0:5000      0.0.0.0:*     users:(("nc",pid=811,fd=3))

    0.0.0.0 significa "en todas las IPs del equipo". Si el servidor escuchara solo en 127.0.0.1, nadie de fuera podría conectar: es un error muy común. (Los & mandan cada programa a segundo plano; tráelos de vuelta con fg o termínalos con kill %1 y kill %2.)

    4.3 UDP: enviar y olvidar

    pc2 · terminal A y B
    pc2# tcpdump -i eth0 -n -X udp
pc2# nc -lu 6001
    pc1
    # Escribe líneas y pulsa Intro: cada línea es un datagrama
pc1# nc -u 10.0.0.2 6001

    No hay saludo previo ni confirmaciones: cada línea viaja en un único datagrama. Ahora envía a un puerto donde nadie escucha:

    pc1
    pc1# scapy
>>> r = sr1(IP(dst="10.0.0.2")/UDP(sport=12345, dport=7777)/b"hola?", timeout=2)
>>> r.summary()
# Y a uno abierto: no hay respuesta automática (UDP no confirma)
>>> send(IP(dst="10.0.0.2")/UDP(sport=12345, dport=6001)/b"hola desde scapy\n")
    'IP / ICMP 10.0.0.2 > 10.0.0.1 dest-unreach port-unreachable / IPerror / UDPerror'

    El kernel de pc2 responde a los puertos UDP cerrados con ICMP "port unreachable". Es la base de nmap -sU y del traceroute clásico.

    4.6 Un handshake TCP hecho a mano (SYN, ACK y datos)

    Ahora el cliente será scapy: escribiremos cada segmento. El servidor será un nc normal en pc2.

    pc2 · terminal A y B
    pc2# tcpdump -i eth0 -n -S tcp port 5002
pc2# nc -l 5002

    Primer intento: el kernel nos sabotea

    scapy en pc1
    >>> ip = IP(dst="10.0.0.2")
>>> syn = TCP(sport=40000, dport=5002, flags="S", seq=1000)
>>> synack = sr1(ip/syn, timeout=2)
>>> synack.summary()

    Recibimos el SYN-ACK… pero en tcpdump aparece un [R] que sale de pc1. ¿Por qué? Scapy envía por su cuenta: el kernel de pc1 no tiene ningún socket abierto en el puerto 40000, así que cuando ve llegar un SYN-ACK inesperado responde RST y mata la conexión.

    Solución: que el kernel de pc1 no envíe RST

    pc1 (fuera de scapy, en otra terminal)
    pc1# iptables -A OUTPUT -p tcp --tcp-flags RST RST -d 10.0.0.2 -j DROP

    Reinicia el servidor nc -l 5002 en pc2 (el RST anterior lo cerró) y repite paso a paso:

    scapy en pc1
    # 1) SYN: "quiero hablar, mi secuencia empieza en 1000"
>>> synack = sr1(ip/TCP(sport=40001, dport=5002, flags="S", seq=1000), timeout=2)
>>> synack[TCP].flags, synack[TCP].seq, synack[TCP].ack
# 2) ACK: confirmo su SYN (su seq + 1). Mi seq ahora es 1001
>>> srv_seq = synack[TCP].seq + 1
>>> send(ip/TCP(sport=40001, dport=5002, flags="A", seq=1001, ack=srv_seq))
    (<Flag 18 (SA)>, 3141592653, 1001)

    La conexión ya está establecida. Compruébalo en pc2: ss -tn muestra ESTAB 10.0.0.2:5002 10.0.0.1:40001.

    scapy en pc1
    # 3) Datos: 17 bytes con PSH+ACK. El nc de pc2 los imprime
>>> datos = b"hola desde scapy\n"
>>> r = sr1(ip/TCP(sport=40001, dport=5002, flags="PA", seq=1001, ack=srv_seq)/datos, timeout=2)
# pc2 confirma: ack = 1001 + 17 = 1018
>>> r[TCP].flags, r[TCP].ack
    (<Flag 16 (A)>, 1018)

    Recibir datos del servidor y confirmarlos

    scapy en pc1 y nc en pc2
    # pc1 se pone a escuchar un segmento del servidor…
>>> p = sniff(iface="eth0", filter="tcp and src port 5002", count=1)[0]
# …y en la terminal del nc de pc2 escribes "hola scapy" + Intro
>>> p[TCP].seq, p[Raw].load
# Confirmamos: ack = su seq + longitud de sus datos
>>> srv_seq = p[TCP].seq + len(p[Raw].load)
>>> send(ip/TCP(sport=40001, dport=5002, flags="A", seq=1018, ack=srv_seq))

    Si tardas en confirmar, verás en tcpdump que pc2 retransmite el mismo segmento varias veces: TCP no da nada por entregado hasta recibir el ACK.

    Cerrar la conexión

    scapy en pc1
    # FIN: he terminado (consume 1 número de secuencia)
>>> r = sr1(ip/TCP(sport=40001, dport=5002, flags="FA", seq=1018, ack=srv_seq), timeout=2)
>>> r[TCP].flags

    pc2 confirma tu FIN y, cuando su nc cierre (o pulses Ctrl+D en él), enviará su propio FIN. Respóndelo con send(ip/TCP(sport=40001, dport=5002, flags="A", seq=1019, ack=SU_SEQ+1)).

    Abortar con RST

    En lugar de FIN, prueba en una conexión nueva a enviar flags="R" con el seq correcto: el servidor la cierra inmediatamente. Con un seq fuera de la ventana el kernel lo ignora: es una protección contra inyecciones de RST.

    pc1 · deshacer
    pc1# iptables -D OUTPUT -p tcp --tcp-flags RST RST -d 10.0.0.2 -j DROP
    Reto: los dos extremos hechos a mano

    Haz lo mismo en pc2 (regla de RST en su OUTPUT hacia 10.0.0.1, sin nc), con scapy en ambos lados: pc2 hace sniff(filter="tcp port 5003", count=1) para recibir el SYN, responde con flags="SA", seq propio y ack=syn.seq+1, y así sucesivamente, igual que hiciste con el ping manual en la capa 2.

    4.7 Estados de conexión: ss y conntrack

    EstadoDóndeSignificado
    LISTENServidorEsperando conexiones
    SYN-SENTClienteEnvió SYN, espera SYN-ACK
    SYN-RECVServidorRecibió SYN, envió SYN-ACK, espera ACK
    ESTABAmbosConexión abierta
    FIN-WAIT-1/2Quien cierraEnvió FIN, espera ACK / FIN del otro
    CLOSE-WAITQuien recibe el FINEl otro cerró; la aplicación aún no

    pc1 / pc2
    # Todas las conexiones TCP con proceso
pc2# ss -tanp
# Solo las de un estado
pc1# ss -tn state time-wait
# Información interna de TCP: RTT, ventana de congestión (cwnd), retransmisiones
pc1# ss -tni
# Resumen
pc1# ss -s

    Los cortafuegos con estado (como el de la capa 3) no miran los estados TCP de los extremos, sino su propia tabla conntrack:

    pc2
    # Una regla cualquiera que use conntrack activa el seguimiento en el namespace
pc2# iptables -A INPUT -m conntrack --ctstate INVALID -j DROP
pc2# conntrack -L
# Ver eventos en directo: NEW, UPDATE, DESTROY
pc2# conntrack -E
    Estado conntrackSignificado
    NEWPrimer paquete de una conexión (un SYN, el primer datagrama UDP)
    ESTABLISHEDYa se ha visto tráfico en los dos sentidos
    RELATEDNueva conexión ligada a otra (ICMP de error, FTP de datos)
    INVALIDNo encaja con nada (p. ej. un ACK sin conexión previa)

    4.8 Redes malas: retardo, pérdidas y ancho de banda

    tc con netem simula enlaces reales. Es la mejor forma de ver cómo TCP reacciona: retransmite, reduce su ritmo y reordena.

    pc1
    # 100 ms de retardo en todo lo que sale de pc1
pc1# tc qdisc add dev eth0 root netem delay 100ms
pc1# ping -c 3 10.0.0.2
# Retardo variable (jitter) y 10% de pérdidas
pc1# tc qdisc change dev eth0 root netem delay 100ms 20ms loss 10%
pc1# ping -c 20 10.0.0.2
# También: duplicar, corromper, reordenar
pc1# tc qdisc change dev eth0 root netem delay 50ms loss 5% duplicate 1% corrupt 1% reorder 10%
pc1# tc qdisc show dev eth0

    Ver a TCP sufrir

    pc2 y pc1
    # Un fichero de 5 MB para enviar
pc1# head -c 5M /dev/urandom > /tmp/lab-5M.bin
# Servidor que recibe y descarta
pc2# nc -l 5004 > /dev/null
# Mira las retransmisiones mientras transfiere (otra terminal de pc2)
pc2# tcpdump -i eth0 -n tcp port 5004
# Enviar y medir el tiempo
pc1# time nc -N 10.0.0.2 5004 < /tmp/lab-5M.bin
# Durante la transferencia, en otra terminal de pc1
pc1# ss -tni dst 10.0.0.2
# Contadores de retransmisiones del namespace
pc1# nstat -az TcpRetransSegs

    Repite la transferencia sin pérdidas, con 1%, con 5% y con 10%: el tiempo no crece de forma lineal. Cada pérdida hace que TCP reduzca su ventana de congestión (cwnd en ss -tni).

    Limitar el ancho de banda

    pc1
    pc1# tc qdisc del dev eth0 root
# 1 Mbit/s con un token bucket
pc1# tc qdisc add dev eth0 root tbf rate 1mbit burst 32kbit latency 400ms
pc1# time nc -N 10.0.0.2 5004 < /tmp/lab-5M.bin
# Quitar cualquier limitación
pc1# tc qdisc del dev eth0 root

    4.10 Protecciones de capa 4

    pc2 (servidor)
    # SYN cookies: el servidor no reserva memoria hasta que el cliente completa el handshake
pc2# sysctl net.ipv4.tcp_syncookies
# Tamaño de la cola de conexiones a medio abrir
pc2# sysctl net.ipv4.tcp_max_syn_backlog
# Limitar conexiones nuevas por segundo a un servicio
pc2# iptables -A INPUT -p tcp --dport 80 --syn -m limit --limit 20/s --limit-burst 40 -j ACCEPT
pc2# iptables -A INPUT -p tcp --dport 80 --syn -j DROP

    Observa con ss -tn state syn-recv las conexiones a medio abrir: en tu prueba de 4.6, si mandas solo el SYN y nunca el ACK, pc2 deja una entrada en ese estado hasta que se agotan sus reintentos de SYN-ACK.
