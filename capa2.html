Capa 2

    Capa 2 · Enlace de datos

    Capa 2: tramas, MAC, ARP y switches

    La capa de enlace mueve tramas entre equipos que están en el mismo medio físico (el mismo cable o el mismo switch). Aquí no hay rutas ni IPs: solo direcciones MAC de 48 bits.

    2.1 Dos ordenadores y un cable

    Vamos a crear dos "ordenadores" (pc1 y pc2) y unirlos con un cable virtual.

    Paso 1: crear los ordenadores

    host
    $ sudo ip netns add pc1
$ sudo ip netns add pc2
$ ip netns list

    Paso 2: crear el cable

    Un par veth nace en el namespace donde lo creas (el host). Tiene dos extremos: veth1 y veth2.

    host
    $ sudo ip link add veth1 type veth peer name veth2
# Los dos extremos aparecen en tu host
$ ip link show type veth

    Paso 3: "enchufar" cada extremo en un ordenador

    host
    $ sudo ip link set veth1 netns pc1
$ sudo ip link set veth2 netns pc2
# Ya no están en el host
$ ip link show type veth

    Paso 4: renombrar y poner MAC fáciles de leer

    Dentro de cada PC llamaremos a la tarjeta eth0, como en un equipo real. Para cambiar el nombre o la MAC la interfaz debe estar apagada (lo está).

    host → pc1
    $ sudo ip netns exec pc1 ip link set veth1 name eth0
$ sudo ip netns exec pc1 ip link set eth0 address 02:00:00:00:00:01
$ sudo ip netns exec pc1 ip link set eth0 up
$ sudo ip netns exec pc1 ip link set lo up
    host → pc2
    $ sudo ip netns exec pc2 ip link set veth2 name eth0
$ sudo ip netns exec pc2 ip link set eth0 address 02:00:00:00:00:02
$ sudo ip netns exec pc2 ip link set eth0 up
$ sudo ip netns exec pc2 ip link set lo up

    Paso 5: comprobar

    pc1
    $ sudo ip netns exec pc1 ip link show eth0
# Más detalle (tipo veth, MTU mínima y máxima…)
$ sudo ip netns exec pc1 ip -d link show eth0
# Estadísticas: tramas y bytes enviados/recibidos, errores, descartes
$ sudo ip netns exec pc1 ip -s link show eth0
    2: eth0@if3: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue state UP mode DEFAULT group default qlen 1000
    link/ether 02:00:00:00:00:01 brd ff:ff:ff:ff:ff:ff link-netns pc2
    CampoSignificado
    eth0@if3Nombre de la interfaz; @if3 es el índice de su pareja veth (en el otro namespace).
    UPAdministrativamente encendida (tú hiciste set up).
    LOWER_UPHay "señal" en el cable: el otro extremo también está encendido. Si apagas pc2, desaparece.
    mtu 1500Tamaño máximo de la carga útil de una trama Ethernet.
    link/ether …Tu dirección MAC.
    brd ff:ff:ff:ff:ff:ffDirección de broadcast de capa 2 (a todos).
    link-netns pc2El otro extremo del cable vive en el namespace pc2.

    Experimento: apaga el extremo de pc2 con sudo ip netns exec pc2 ip link set eth0 down y mira de nuevo pc1: verás NO-CARRIER y state LOWERLAYERDOWN, igual que al desenchufar un cable. Vuelve a encenderlo con up.

    2.2 Anatomía de una trama Ethernet

    Tipos de dirección MAC

    TipoCómo se reconoceEjemploQuién la recibe
    UnicastBit menos significativo del 1er byte = 002:00:00:00:00:01Una sola tarjeta
    MulticastBit menos significativo del 1er byte = 101:00:5e:00:00:01Las tarjetas suscritas al grupo
    BroadcastTodo a unosff:ff:ff:ff:ff:ffTodas las del segmento
    Administrada localmente2º bit del 1er byte = 1 (02, 06, 0a, 0e…)02:…Puesta a mano / virtual
    Global (de fábrica)2º bit = 0; los 3 primeros bytes son el fabricante (OUI)3c:52:82:…Asignada por el fabricante

    2.3 Comunicarse solo en capa 2 (sin IP)

    Los PCs aún no tienen IP. Aun así pueden hablar: basta con mandar una trama con la MAC de destino. Lo haremos con scapy, una consola de Python para fabricar paquetes.

    Terminal A: escuchar en pc2

    -e muestra la cabecera Ethernet (las MAC), -n no traduce nombres, -X enseña el contenido en hexadecimal y ASCII.

    pc2 · terminal A
    $ sudo ip netns exec pc2 tcpdump -i eth0 -e -n -X

    Terminal B: abrir scapy en pc1

    pc1 · terminal B
    $ sudo ip netns exec pc1 scapy

    Dentro de scapy (el prompt es >>>) construimos la trama campo a campo:

    scapy en pc1
    # Una trama Ethernet: destino pc2, origen pc1, tipo experimental
>>> t = Ether(dst="02:00:00:00:00:02", src="02:00:00:00:00:01", type=0x88b5)
# Le pegamos (/) una carga útil de texto
>>> t = t / Raw(load=b"Hola pc2, soy pc1 en capa 2")
# Ver la trama campo a campo
>>> t.show()
# Ver los bytes exactos que viajarán por el cable
>>> hexdump(t)
# sendp = enviar en capa 2 (la "p" es de "packet at layer 2")
>>> sendp(t, iface="eth0")

    En la terminal A aparece:

    12:00:01.000 02:00:00:00:00:01 > 02:00:00:00:00:02, ethertype Unknown (0x88b5), length 41:
	0x0000:  486f 6c61 2070 6332 2c20 736f 7920 7063  Hola.pc2,.soy.pc
	0x0010:  3120 656e 2063 6170 6120 32              1.en.capa.2

    Acabas de comunicar dos ordenadores sin IP, sin puertos, sin nada: solo MAC origen, MAC destino, tipo y datos. Así es la capa 2.

    Broadcast y MAC ajenas

    scapy en pc1
    # A todos (broadcast): pc2 lo recibe
>>> sendp(Ether(dst="ff:ff:ff:ff:ff:ff", type=0x88b5)/Raw(load=b"a todos"), iface="eth0")
# A una MAC que no es la de pc2: tcpdump la ve porque pone la tarjeta en modo promiscuo
>>> sendp(Ether(dst="02:00:00:00:00:99", type=0x88b5)/Raw(load=b"no es para ti"), iface="eth0")

    Modo promiscuo: normalmente una tarjeta descarta las tramas cuya MAC destino no es la suya, broadcast o multicast suscrito. tcpdump activa el modo promiscuo para verlo todo. Prueba con tcpdump -p (sin promiscuo) y el último envío ya no aparecerá. Puedes activarlo a mano con ip link set eth0 promisc on.

    Recibir con scapy en lugar de tcpdump

    scapy en pc2
    $ sudo ip netns exec pc2 scapy
# Espera 1 trama del tipo 0x88b5 y guárdala
>>> r = sniff(iface="eth0", filter="ether proto 0x88b5", count=1)
>>> r[0].show()
>>> r[0][Raw].load

    Con scapy en pc2 escuchando y scapy en pc1 enviando, ya tienes un "chat" en capa 2. Contesta desde pc2 con sendp(Ether(dst=r[0].src, type=0x88b5)/Raw(load=b"recibido"), iface="eth0").

    2.4 ARP: de IP a MAC

    Las aplicaciones usan direcciones IP, pero el cable solo entiende MAC. ARP (Address Resolution Protocol) pregunta "¿quién tiene la IP X? dímelo a mí" por broadcast, y el dueño responde con su MAC. La respuesta se guarda en la tabla ARP (tabla de vecinos).

    Paso 1: poner IPs

    host
    $ sudo ip netns exec pc1 ip addr add 10.0.0.1/24 dev eth0
$ sudo ip netns exec pc2 ip addr add 10.0.0.2/24 dev eth0
$ sudo ip netns exec pc1 ip addr show eth0

    Paso 2: mirar la tabla ARP (vacía)

    pc1
    $ sudo ip netns exec pc1 ip neigh show

    Paso 3: capturar mientras se hace un ping

    pc2 · terminal A
    $ sudo ip netns exec pc2 tcpdump -i eth0 -e -n arp or icmp
    pc1 · terminal B
    $ sudo ip netns exec pc1 ping -c 1 10.0.0.2
$ sudo ip netns exec pc1 ip neigh show
    02:00:00:00:00:01 > ff:ff:ff:ff:ff:ff, ethertype ARP (0x0806), length 42: Request who-has 10.0.0.2 tell 10.0.0.1, length 28
02:00:00:00:00:02 > 02:00:00:00:00:01, ethertype ARP (0x0806), length 42: Reply 10.0.0.2 is-at 02:00:00:00:00:02, length 28
02:00:00:00:00:01 > 02:00:00:00:00:02, ethertype IPv4 (0x0800), length 98: 10.0.0.1 > 10.0.0.2: ICMP echo request, id 4242, seq 1, length 64
02:00:00:00:00:02 > 02:00:00:00:00:01, ethertype IPv4 (0x0800), length 98: 10.0.0.2 > 10.0.0.1: ICMP echo reply, id 4242, seq 1, length 64

10.0.0.2 dev eth0 lladdr 02:00:00:00:00:02 REACHABLE

    Formato de un mensaje ARP

    CampoRequest (pc1)Reply (pc2)
    Ethernet destinoff:ff:ff:ff:ff:ff02:00:00:00:00:01
    Ethernet origen02:00:00:00:00:0102:00:00:00:00:02
    EtherType0x0806
    hwtype / ptype1 (Ethernet) / 0x0800 (IPv4)
    op1 (who-has)2 (is-at)
    hwsrc (MAC emisor)02:00:00:00:00:0102:00:00:00:00:02
    psrc (IP emisor)10.0.0.110.0.0.2
    hwdst (MAC objetivo)00:00:00:00:00:00 (desconocida)02:00:00:00:00:01
    pdst (IP objetivo)10.0.0.210.0.0.1

    Estados de la tabla de vecinos

    EstadoSignificado
    INCOMPLETESe ha enviado el ARP Request y aún no hay respuesta.
    REACHABLEMAC confirmada recientemente (unos 30 s).
    STALEHace tiempo que no se confirma; se sigue usando pero se verificará al volver a enviar.
    DELAY / PROBEVerificando una entrada STALE (primero espera, luego pregunta en unicast).
    FAILEDNadie respondió: el equipo no existe o no contesta.
    PERMANENTEntrada estática puesta a mano. No caduca.

    Manipular la tabla ARP

    pc1
    # Ver con detalle (incluye contadores y tiempos)
$ sudo ip netns exec pc1 ip -s neigh show
# Borrar todas las entradas de eth0
$ sudo ip netns exec pc1 ip neigh flush dev eth0
# Ping a una IP que no existe: verás INCOMPLETE y luego FAILED
$ sudo ip netns exec pc1 ping -c 2 10.0.0.50
$ sudo ip netns exec pc1 ip neigh show
# Entrada estática (permanente)
$ sudo ip netns exec pc1 ip neigh add 10.0.0.2 lladdr 02:00:00:00:00:02 dev eth0 nud permanent
# Cambiarla o borrarla
$ sudo ip netns exec pc1 ip neigh replace 10.0.0.2 lladdr 02:00:00:00:00:02 dev eth0 nud reachable
$ sudo ip netns exec pc1 ip neigh del 10.0.0.2 dev eth0

    arping: hablar ARP directamente

    pc1
    # "Ping" de capa 2: pregunta la MAC de 10.0.0.2 tres veces
$ sudo ip netns exec pc1 arping -I eth0 -c 3 10.0.0.2
# Detección de IP duplicada (DAD): ¿alguien usa ya 10.0.0.2?
$ sudo ip netns exec pc1 arping -I eth0 -D -c 2 10.0.0.2
# ARP gratuito: anunciar mi propia IP/MAC a todos (se usa al cambiar de MAC o en failover)
$ sudo ip netns exec pc1 arping -I eth0 -U -c 2 10.0.0.1

    Fíjate en que si arping -D obtiene respuesta, devuelve código de error 1: significa "esa IP está ocupada". Lo usan los clientes DHCP antes de configurar una IP.

    2.5 Un ping desmontado pieza a pieza (en los dos PCs)

    Ahora vamos a hacer a mano todo lo que hace el kernel durante un ping: el ARP Request, el ARP Reply, el Echo Request y el Echo Reply. Para que el kernel de pc2 no conteste por nosotros, le quitamos esas funciones.

    Preparación: silenciar el kernel de pc2

    pc2
    # La interfaz deja de responder ARP (flag NOARP)
$ sudo ip netns exec pc2 ip link set dev eth0 arp off
# El kernel deja de responder pings
$ sudo ip netns exec pc2 sysctl -w net.ipv4.icmp_echo_ignore_all=1
# pc1 olvida lo que sabía
$ sudo ip netns exec pc1 ip neigh flush dev eth0

    Comprueba que el ping normal ya no funciona: sudo ip netns exec pc1 ping -c 2 10.0.0.2 → 100% pérdida.

    Abre tres terminales: una con tcpdump para ver todo, y una con scapy en cada PC.

    terminal 1 · observador en pc2
    $ sudo ip netns exec pc2 tcpdump -i eth0 -e -n -v
    terminal 2 y 3
    $ sudo ip netns exec pc1 scapy
$ sudo ip netns exec pc2 scapy

    Paso 1 · pc1 pregunta por ARP

    Preparamos la pregunta y la enviamos con srp1: envía en capa 2 y espera la primera respuesta que encaje (hasta 120 s).

    scapy en pc1
    >>> pregunta = Ether(dst="ff:ff:ff:ff:ff:ff", src="02:00:00:00:00:01") / ARP(op=1, hwsrc="02:00:00:00:00:01", psrc="10.0.0.1", pdst="10.0.0.2")
>>> pregunta.show()
>>> resp = srp1(pregunta, iface="eth0", timeout=120)

    pc1 se queda esperando. En tcpdump verás el Request who-has 10.0.0.2 tell 10.0.0.1 y ninguna respuesta.

    Paso 2 · pc2 responde a mano

    scapy en pc2
    >>> respuesta = Ether(dst="02:00:00:00:00:01", src="02:00:00:00:00:02") / ARP(op=2, hwsrc="02:00:00:00:00:02", psrc="10.0.0.2", hwdst="02:00:00:00:00:01", pdst="10.0.0.1")
>>> sendp(respuesta, iface="eth0")

    En pc1, srp1 termina. Veamos qué recibió:

    scapy en pc1
    >>> resp.show()
>>> mac_pc2 = resp[ARP].hwsrc
>>> mac_pc2
    '02:00:00:00:00:02'

    Paso 3 · pc2 se pone a escuchar y pc1 envía el Echo Request

    Primero pc2 se queda esperando un paquete ICMP:

    scapy en pc2
    >>> p = sniff(iface="eth0", filter="icmp", count=1)[0]

    Luego pc1 construye el ping capa por capa: Ethernet (con la MAC que aprendimos) / IP / ICMP / datos:

    scapy en pc1
    >>> eco = Ether(dst=mac_pc2, src="02:00:00:00:00:01") / IP(src="10.0.0.1", dst="10.0.0.2", ttl=64) / ICMP(type=8, code=0, id=0x1234, seq=1) / Raw(load=b"ping hecho a mano")
# show2() muestra el paquete con los checksums y longitudes ya calculados
>>> eco.show2()
>>> resp = srp1(eco, iface="eth0", timeout=120)

    Paso 4 · pc2 construye el Echo Reply a partir de lo recibido

    El sniff de pc2 ha terminado. Inspeccionamos el paquete y contestamos dándole la vuelta a las direcciones y copiando id, seq y datos (así lo exige el protocolo ICMP):

    scapy en pc2
    >>> p.show()
>>> p[ICMP].id, p[ICMP].seq, p[Raw].load
>>> eco_resp = Ether(dst=p[Ether].src, src=p[Ether].dst) / IP(src=p[IP].dst, dst=p[IP].src, ttl=64) / ICMP(type=0, code=0, id=p[ICMP].id, seq=p[ICMP].seq) / Raw(load=p[Raw].load)
>>> sendp(eco_resp, iface="eth0")

    pc1 recibe la respuesta:

    scapy en pc1
    >>> resp.show()
>>> resp[ICMP].type
>>> resp[Raw].load
    0
b'ping hecho a mano'

    Has hecho un ping completo escribiendo tú las 4 piezas. Esto es exactamente lo que hacen los kernels de ambos equipos en microsegundos cada vez que escribes ping.

    Los campos de ICMP que has rellenado

    CampoEcho RequestEcho ReplyPara qué sirve
    type80Tipo de mensaje ICMP
    code00Subtipo
    checksumLo calcula scapyDetectar corrupción
    idigual en ambos (0x1234)Distinguir pings de distintos procesos
    seqigual en ambos (1)Número de ping (1, 2, 3…)
    datosse devuelven idénticosMedir RTT, detectar corrupción

    Variante: dejar que pc1 use su kernel

    Pon una entrada ARP estática en pc1 (ip neigh add 10.0.0.2 lladdr 02:00:00:00:00:02 dev eth0 nud permanent) y lanza un ping normal desde pc1 con ping -c 1 10.0.0.2. En pc2 repite el paso 4 (sniff + respuesta). Verás que ping acepta tu respuesta artesanal y calcula el tiempo.

    El id lo elige el programa ping; por eso en pc2 lo copiamos del paquete recibido en lugar de inventarlo.

    Restaurar pc2

    pc2
    $ sudo ip netns exec pc2 ip link set dev eth0 arp on
$ sudo ip netns exec pc2 sysctl -w net.ipv4.icmp_echo_ignore_all=0
$ sudo ip netns exec pc1 ip neigh flush dev eth0
$ sudo ip netns exec pc1 ping -c 2 10.0.0.2

    2.6 Un switch con tres PCs

    Con dos equipos basta un cable. Con más, hace falta un switch. En Linux un switch es un bridge. Lo meteremos en su propio namespace sw para que se vea como un aparato más.

    Empieza de cero:

    host
    $ sudo ip netns del pc1
$ sudo ip netns del pc2

    Paso 1: crear los cuatro aparatos

    host
    $ sudo ip netns add sw
$ sudo ip netns add pc1
$ sudo ip netns add pc2
$ sudo ip netns add pc3

    Paso 2: crear el switch

    sw
    $ sudo ip netns exec sw ip link add br0 type bridge
$ sudo ip netns exec sw ip link set br0 up

    Paso 3: tres cables, creando cada extremo directamente en su namespace

    Atajo: ip link add permite decir en qué namespace nace cada extremo.

    host
    $ sudo ip link add eth0 netns pc1 type veth peer name p1 netns sw
$ sudo ip link add eth0 netns pc2 type veth peer name p2 netns sw
$ sudo ip link add eth0 netns pc3 type veth peer name p3 netns sw

    Paso 4: conectar los puertos al switch

    master br0 = "este puerto pertenece al bridge br0".

    sw
    $ sudo ip netns exec sw ip link set p1 master br0
$ sudo ip netns exec sw ip link set p2 master br0
$ sudo ip netns exec sw ip link set p3 master br0
$ sudo ip netns exec sw ip link set p1 up
$ sudo ip netns exec sw ip link set p2 up
$ sudo ip netns exec sw ip link set p3 up
# Ver los puertos del bridge
$ sudo ip netns exec sw bridge link show

    Paso 5: configurar los PCs

    pc1
    $ sudo ip netns exec pc1 ip link set eth0 address 02:00:00:00:00:01
$ sudo ip netns exec pc1 ip addr add 10.0.0.1/24 dev eth0
$ sudo ip netns exec pc1 ip link set eth0 up
$ sudo ip netns exec pc1 ip link set lo up
    pc2
    $ sudo ip netns exec pc2 ip link set eth0 address 02:00:00:00:00:02
$ sudo ip netns exec pc2 ip addr add 10.0.0.2/24 dev eth0
$ sudo ip netns exec pc2 ip link set eth0 up
$ sudo ip netns exec pc2 ip link set lo up
    pc3
    $ sudo ip netns exec pc3 ip link set eth0 address 02:00:00:00:00:03
$ sudo ip netns exec pc3 ip addr add 10.0.0.3/24 dev eth0
$ sudo ip netns exec pc3 ip link set eth0 up
$ sudo ip netns exec pc3 ip link set lo up

    Paso 6: cómo aprende un switch (tabla FDB)

    Un switch apunta en su FDB (Forwarding DataBase) en qué puerto ha visto cada MAC de origen. Si no conoce el destino, inunda (flooding): reenvía la trama por todos los puertos menos por el que entró.

    sw
    # Antes de tráfico: solo las MAC propias de los puertos (marcadas "permanent")
$ sudo ip netns exec sw bridge fdb show br br0

    Pon a pc3 a escuchar (es un "espía" que no participa) y haz ping de pc1 a pc2:

    pc3 · terminal A
    $ sudo ip netns exec pc3 tcpdump -i eth0 -e -n
    pc1 · terminal B
    $ sudo ip netns exec pc1 ping -c 3 10.0.0.2

    pc3 solo ve el ARP Request (broadcast). Los pings, que van en unicast a una MAC ya aprendida, no le llegan. Ahora mira la FDB:

    sw
    $ sudo ip netns exec sw bridge fdb show br br0 dynamic
    02:00:00:00:00:01 dev p1 master br0
02:00:00:00:00:02 dev p2 master br0
    SituaciónQué hace el switch
    MAC destino en la FDBReenvía solo por ese puerto (forwarding)
    MAC destino desconocidaInunda por todos los puertos excepto el de entrada (unknown unicast flooding)
    Broadcast ff:ff:…Inunda siempre
    Destino en el mismo puerto de entradaDescarta (filtering)
    Entrada sin tráfico durante el ageing timeLa borra (300 s por defecto)
    sw
    # Ver parámetros del bridge (ageing_time está en centésimas de segundo)
$ sudo ip netns exec sw ip -d link show br0
# Bajar el tiempo de envejecimiento a 10 s para verlo caducar
$ sudo ip netns exec sw ip link set br0 type bridge ageing_time 1000
# Añadir una entrada estática (como en un switch gestionable)
$ sudo ip netns exec sw bridge fdb add 02:00:00:00:00:03 dev p3 master static
# Borrar la entrada
$ sudo ip netns exec sw bridge fdb del 02:00:00:00:00:03 dev p3 master static

    Experimento: el switch "tonto" (hub)

    Si desactivas el aprendizaje de MAC en los puertos, el bridge no sabe dónde está nadie y se comporta como un hub: inunda todo. Vacía la FDB, repite el ping de pc1 a pc2 y pc3 verá también los ICMP.

    sw
    $ sudo ip netns exec sw ip link set p1 type bridge_slave learning off
$ sudo ip netns exec sw ip link set p2 type bridge_slave learning off
$ sudo ip netns exec sw ip link set p3 type bridge_slave learning off
$ sudo ip netns exec sw ip link set br0 type bridge fdb_flush
# Volver a la normalidad
$ sudo ip netns exec sw ip link set p1 type bridge_slave learning on
$ sudo ip netns exec sw ip link set p2 type bridge_slave learning on
$ sudo ip netns exec sw ip link set p3 type bridge_slave learning on
$ sudo ip netns exec sw ip link set br0 type bridge ageing_time 30000

    Desconectar un puerto

    sw
    $ sudo ip netns exec sw ip link set p2 down
$ sudo ip netns exec pc1 ping -c 2 10.0.0.2
$ sudo ip netns exec sw ip link set p2 up

    2.7 VLAN: varias redes en un mismo switch

    Una VLAN divide un switch en varios switches lógicos. Las tramas de VLAN 10 nunca llegan a puertos de VLAN 20. Usaremos el mismo switch: pc1 y pc2 en VLAN 10, pc3 en VLAN 20.

    sw
    # Activar el filtrado por VLAN en el bridge
$ sudo ip netns exec sw ip link set br0 type bridge vlan_filtering 1
# Por defecto todos los puertos están en la VLAN 1. Míralo:
$ sudo ip netns exec sw bridge vlan show
# p1 y p2: puertos de acceso en VLAN 10 (pvid = VLAN para lo que entra sin etiqueta; untagged = sale sin etiqueta)
$ sudo ip netns exec sw bridge vlan add dev p1 vid 10 pvid untagged
$ sudo ip netns exec sw bridge vlan del dev p1 vid 1
$ sudo ip netns exec sw bridge vlan add dev p2 vid 10 pvid untagged
$ sudo ip netns exec sw bridge vlan del dev p2 vid 1
# p3: VLAN 20
$ sudo ip netns exec sw bridge vlan add dev p3 vid 20 pvid untagged
$ sudo ip netns exec sw bridge vlan del dev p3 vid 1
$ sudo ip netns exec sw bridge vlan show
    pruebas
    # Funciona (misma VLAN)
$ sudo ip netns exec pc1 ping -c 2 10.0.0.2
# No funciona (distinta VLAN, aunque misma subred IP)
$ sudo ip netns exec pc1 ping -c 2 10.0.0.3

    Puerto troncal (trunk) y etiquetas 802.1Q

    Un puerto trunk transporta varias VLAN a la vez añadiendo una etiqueta de 4 bytes a cada trama. Convertimos p3 en troncal (VLAN 10 y 20 etiquetadas) y en pc3 creamos dos subinterfaces, una por VLAN.

    sw
    $ sudo ip netns exec sw bridge vlan del dev p3 vid 20
$ sudo ip netns exec sw bridge vlan add dev p3 vid 10
$ sudo ip netns exec sw bridge vlan add dev p3 vid 20
    pc3
    $ sudo ip netns exec pc3 ip addr flush dev eth0
$ sudo ip netns exec pc3 ip link add link eth0 name eth0.10 type vlan id 10
$ sudo ip netns exec pc3 ip link add link eth0 name eth0.20 type vlan id 20
$ sudo ip netns exec pc3 ip addr add 10.0.0.3/24 dev eth0.10
$ sudo ip netns exec pc3 ip addr add 10.20.0.3/24 dev eth0.20
$ sudo ip netns exec pc3 ip link set eth0.10 up
$ sudo ip netns exec pc3 ip link set eth0.20 up
    pc3
    # Mira las etiquetas en el cable físico (eth0)
$ sudo ip netns exec pc3 tcpdump -i eth0 -e -n

    MTU y tramas jumbo

    pc1 / pc2
    # Un ping de 1472 bytes de datos + 8 ICMP + 20 IP = 1500 justo. -M do prohíbe fragmentar
$ sudo ip netns exec pc1 ping -c 1 -M do -s 1472 10.0.0.2
# 1473 ya no cabe
$ sudo ip netns exec pc1 ping -c 1 -M do -s 1473 10.0.0.2
# Subir la MTU a 9000 (jumbo). Debe hacerse en todos los equipos y puertos del segmento
$ sudo ip netns exec pc1 ip link set eth0 mtu 9000

    Si cambias la MTU solo en un lado, los paquetes grandes se pierden en silencio. Es uno de los fallos más típicos en redes reales.

    Cambiar la MAC de un equipo

    pc2
    $ sudo ip netns exec pc2 ip link set eth0 down
$ sudo ip netns exec pc2 ip link set eth0 address 02:00:00:00:00:22
$ sudo ip netns exec pc2 ip link set eth0 up
# Anunciar la nueva MAC para que los vecinos actualicen su tabla ARP
$ sudo ip netns exec pc2 arping -I eth0 -U -c 1 10.0.0.2
$ sudo ip netns exec pc1 ip neigh show

    Spanning Tree (STP): evitar bucles

    Si unes dos switches con dos cables, las tramas broadcast dan vueltas para siempre (tormenta de broadcast). STP bloquea los enlaces redundantes.

    sw
    $ sudo ip netns exec sw ip link set br0 type bridge stp_state 1
# Ver el estado de cada puerto: forwarding, blocking, learning…
$ sudo ip netns exec sw bridge link show
    Laboratorio opcional: bucle con dos switches

    Crea un segundo switch sw2 con su bridge, únelo a sw con dos cables (dos pares veth) y conecta un PC a cada switch. Sin STP, un solo arping dispara los contadores de ip -s link a miles de tramas por segundo. Activa stp_state 1 en ambos bridges, espera ~30 s y verás con bridge link show que uno de los puertos queda en estado blocking.
