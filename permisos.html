    Permisos: quién puede hacer qué en la red

    Una red no es solo cables y protocolos: también hay que decidir quién puede administrar un router, entrar en un servidor o usar un servicio. Aquí vemos los mecanismos, de lo más local (sudo en un equipo) a lo más centralizado (un directorio tipo Active Directory).

    Esta página crea un usuario real (alumno) y un fichero de sudoers en tu Arch. Todo se deshace en la limpieza final.

    P.1 Modo administrador: root y privilegios de red

    En Linux, root (UID 0) puede hacerlo todo. Por eso ip netns add, ip link, iptables o tcpdump necesitan sudo. En realidad el kernel no pregunta "¿eres root?", sino "¿tienes la capability necesaria?":

    CapabilityPermiteEjemplos
    CAP_NET_ADMINConfigurar la redip addr add, ip route, iptables, tc
    CAP_NET_RAWSockets crudos: fabricar o capturar paquetestcpdump, scapy, arping, nmap -sS
    CAP_NET_BIND_SERVICEEscuchar en puertos < 1024Servidor web en el 80
    CAP_SYS_ADMINMuchas cosas, entre ellas cambiar de namespaceip netns exec
    host
    # Quién soy y a qué grupos pertenezco
$ id
# Qué me deja hacer sudo
$ sudo -l
# Las capabilities de mi shell actual (normal: ninguna) y de una shell root
$ grep Cap /proc/self/status
$ sudo grep Cap /proc/self/status

    P.2 sudo: delegar solo lo necesario

    Queremos que alumno pueda consultar la red de pc1 y hacer pings desde allí, pero no cambiar nada ni abrir una shell de root. Es el principio de mínimo privilegio.

    Las reglas de sudo se editan siempre con visudo, que comprueba la sintaxis antes de guardar (un error en sudoers te puede dejar sin sudo):

    host
    $ sudo EDITOR=nano visudo -f /etc/sudoers.d/lab-redes

    Escribe esto en el fichero:

    /etc/sudoers.d/lab-redes
    # Comandos de solo lectura y diagnóstico en pc1
Cmnd_Alias RED_CONSULTA = /usr/bin/ip netns list, \
                          /usr/bin/ip netns exec pc1 /usr/bin/ip addr show, \
                          /usr/bin/ip netns exec pc1 /usr/bin/ip route show, \
                          /usr/bin/ip netns exec pc1 /usr/bin/ip neigh show
Cmnd_Alias RED_PING     = /usr/bin/ip netns exec pc1 /usr/bin/ping -c [1-9] 10.0.0.*

# El grupo "redes" puede ejecutarlos como root, sin contraseña
%redes ALL=(root) NOPASSWD: RED_CONSULTA, RED_PING
    host · probar como alumno
    $ sudo -iu alumno
alumno$ sudo -l
alumno$ sudo ip netns exec pc1 ip addr show
alumno$ sudo ip netns exec pc1 ping -c 2 10.0.0.2
# Todo esto debe ser denegado:
alumno$ sudo ip netns exec pc1 ip addr add 10.0.0.9/24 dev eth0
alumno$ sudo ip netns exec pc1 bash
alumno$ sudo ip netns exec pc1 ping 10.0.0.2
alumno$ exit
    host · auditoría
    # sudo registra cada uso, permitido o no
$ sudo journalctl _COMM=sudo -n 20
    Sintaxis sudoersSignificado
    usuario HOST=(COMO_QUIEN) COMANDOSForma general de una regla
    %grupoRegla para todos los miembros de un grupo
    NOPASSWD:No pedir contraseña
    Cmnd_Alias, User_AliasAgrupar comandos o usuarios
    Ruta completa + argumentosSolo ese comando con esos argumentos (comodines *, [1-9])
    Ruta sin argumentosEse comando con cualquier argumento
    "" como argumentosEl comando sin ningún argumento

    Trampas típicas que equivalen a dar root completo:

    • /usr/bin/ip netns exec pc1 *: permite ip netns exec pc1 bash.
    • /usr/bin/tcpdump con cualquier argumento: su opción -z ejecuta un programa al rotar ficheros.
    • /usr/bin/nmap: sus scripts NSE (--script) son código Lua arbitrario.
    • Editores, less, find, python… pueden abrir una shell.
    • Un * en los argumentos también casa con espacios, es decir, con argumentos extra: úsalo con cuidado.

    Por eso en la regla anterior fijamos exactamente los argumentos.

    P.3 Capabilities: privilegios sin ser root

    En lugar de dar root, se puede dar a un programa solo la capability que necesita. Hacemos una copia de tcpdump que cualquier usuario puede usar para capturar:

    host
    # La copia va en tu home: /tmp suele montarse con nosuid, y ahí las capabilities se ignoran
$ cp /usr/bin/tcpdump ~/lab-tcpdump
# Sin capability: falla
$ ~/lab-tcpdump -i lo -c 2
# Le damos permiso para capturar (raw) y poner la interfaz en promiscuo (admin)
$ sudo setcap cap_net_raw,cap_net_admin=eip ~/lab-tcpdump
$ getcap ~/lab-tcpdump
# Ahora funciona como usuario normal (en otra terminal: ping -c 2 127.0.0.1)
$ ~/lab-tcpdump -i lo -c 2
    host · ver qué binarios del sistema tienen capabilities
    $ getcap -r /usr/bin 2>/dev/null

    Puertos privilegiados por namespace

    El límite de "solo root escucha en puertos < 1024" es un ajuste de cada namespace de red:

    host
    # alumno intenta abrir un servidor en el puerto 80 de pc2: PermissionError
$ sudo ip netns exec pc2 sudo -u alumno python -m http.server 80 --directory /tmp
$ sudo ip netns exec pc2 sysctl net.ipv4.ip_unprivileged_port_start
# En pc2 (y solo en pc2), los puertos desde el 80 son para todos
$ sudo ip netns exec pc2 sysctl -w net.ipv4.ip_unprivileged_port_start=80
$ sudo ip netns exec pc2 sudo -u alumno python -m http.server 80 --directory /tmp

    Comprueba con sudo ip netns exec pc2 ss -tlpn que el proceso pertenece a alumno, y que en tu host el límite sigue en 1024.

    P.4 Cortafuegos por usuario

    iptables puede filtrar el tráfico que genera un equipo según el usuario o grupo del proceso (módulo owner, solo en OUTPUT). Con el servidor de alumno en pc2:80 en marcha:

    host
    # En pc1: los procesos de alumno no pueden ir a la web de pc2
$ sudo ip netns exec pc1 iptables -A OUTPUT -m owner --uid-owner alumno -p tcp -d 10.0.0.2 --dport 80 -j REJECT
# root sí puede
$ sudo ip netns exec pc1 curl -s http://10.0.0.2/ | head -3
# alumno no: "Connection refused"
$ sudo ip netns exec pc1 sudo -u alumno curl http://10.0.0.2/
# Por grupo: nadie del grupo redes puede hacer ping fuera
$ sudo ip netns exec pc1 iptables -A OUTPUT -m owner --gid-owner redes -p icmp -j DROP
$ sudo ip netns exec pc1 iptables -L OUTPUT -n -v

    Esto es lo que hacen, a mayor escala, los cortafuegos de "identidad" corporativos: reglas por usuario o grupo en vez de por IP.

    P.5 Acceso remoto con SSH: claves y grupos

    Montamos en pc2 un servidor SSH con una política estricta: sin contraseñas, sin root, solo el grupo redes. Usamos una configuración propia para no tocar la del sistema.

    host
    $ sudo mkdir -p /tmp/lab-ssh
$ sudo ssh-keygen -t ed25519 -N "" -f /tmp/lab-ssh/host_key
$ sudo nano /tmp/lab-ssh/sshd_config

$ sudo ip netns exec pc2 /usr/bin/sshd -t -f /tmp/lab-ssh/sshd_config
$ sudo ip netns exec pc2 /usr/bin/sshd -D -e -f /tmp/lab-ssh/sshd_config

    La clave de alumno

    host · como alumno
    $ sudo -iu alumno
alumno$ ssh-keygen -t ed25519 -N "" -f ~/.ssh/id_ed25519
# "Instalar" la clave pública en el servidor (aquí es el mismo disco)
alumno$ cp ~/.ssh/id_ed25519.pub ~/.ssh/authorized_keys
alumno$ chmod 600 ~/.ssh/authorized_keys
alumno$ exit
    host · conectar desde pc1
    # alumno: entra con su clave
$ sudo ip netns exec pc1 sudo -iu alumno ssh alumno@10.0.0.2 hostname
# Tu usuario (no está en "redes"): rechazado
$ sudo ip netns exec pc1 sudo -u $USER ssh $USER@10.0.0.2

    En los logs de sshd verás Accepted publickey for alumno … ED25519 SHA256:… y, para tu usuario, User … not allowed because none of user's groups are listed in AllowGroups.

    Directiva sshdEfecto
    PermitRootLogin noNadie entra directamente como root (se entra como usuario y se usa sudo: queda registro de quién)
    PasswordAuthentication noSolo claves: inmune a adivinar contraseñas
    AllowGroups / AllowUsersLista blanca de quién puede entrar
    Match Group X + ForceCommandUn grupo solo puede ejecutar un comando concreto
    AllowTcpForwarding noProhíbe túneles -L/-R/-D
    ListenAddress 10.0.0.2Escuchar solo en una interfaz (p. ej. la de gestión)

    El problema de escala: aquí funciona porque pc1 y pc2 comparten disco y usuarios con tu host. En una red real cada servidor tiene sus propios usuarios: dar de alta a alguien en 200 servidores, o quitarle el acceso cuando se va de la empresa, es inviable a mano. Para eso existe un directorio centralizado.

    P.6 Directorio centralizado: LDAP, el corazón de Active Directory

    Active Directory (AD) de Microsoft no es un único protocolo, sino un conjunto de servicios estándar trabajando juntos:

    Pieza de ADProtocolo / estándarPuertoEquivalente libre
    Directorio de usuarios, grupos, equiposLDAP389 (636 LDAPS)OpenLDAP, 389-DS, Samba AD
    Autenticación con tickets (inicio de sesión único)Kerberos88MIT Kerberos, Heimdal
    Localizar los controladores de dominioDNS (registros SRV)53BIND, dnsmasq, DNS interno de Samba
    Políticas de grupo (GPO)SMB + LDAP445Samba (parcial), Ansible/Salt en Linux
    Hora sincronizada (Kerberos la exige)NTP123chrony, ntpd
    Integración de clientes Linux——SSSD, realmd, winbind

    estacion
    # "Iniciar sesión" (bind) como ana y preguntar quién soy
$ sudo ip netns exec estacion ldapwhoami -x -H ldap://10.0.20.1 -D "uid=ana,ou=usuarios,dc=lab,dc=local" -w ana123
# Contraseña errónea: "Invalid credentials (49)"
$ sudo ip netns exec estacion ldapwhoami -x -H ldap://10.0.20.1 -D "uid=ana,ou=usuarios,dc=lab,dc=local" -w mal

$ sudo ip netns exec estacion ldapsearch -x -H ldap://10.0.20.1 -D "uid=ana,ou=usuarios,dc=lab,dc=local" -w ana123 -b "ou=usuarios,dc=lab,dc=local" "(uid=luis)" cn mail
# ¿A qué grupos pertenece ana? (lo que pregunta un servidor antes de dejarla entrar)
$ sudo ip netns exec estacion ldapsearch -x -H ldap://10.0.20.1 -D "uid=ana,ou=usuarios,dc=lab,dc=local" -w ana123 -b "ou=grupos,dc=lab,dc=local" "(member=uid=ana,ou=usuarios,dc=lab,dc=local)" cn
# ana intenta leer la contraseña (hash) de luis: no aparece
$ sudo ip netns exec estacion ldapsearch -x -H ldap://10.0.20.1 -D "uid=ana,ou=usuarios,dc=lab,dc=local" -w ana123 -b "uid=luis,ou=usuarios,dc=lab,dc=local" userPassword

    Dar a luis permisos de administrador de red = añadirlo al grupo. Crea /tmp/lab-ldap/luis-admin.ldif:

    /tmp/lab-ldap/luis-admin.ldif

    $ sudo ip netns exec estacion ldapmodify -x -H ldap://10.0.20.1 -D "cn=admin,dc=lab,dc=local" -W -f /tmp/lab-ldap/luis-admin.ldif
# Comprobar los miembros del grupo
$ sudo ip netns exec estacion ldapsearch -x -H ldap://10.0.20.1 -D "uid=ana,ou=usuarios,dc=lab,dc=local" -w ana123 -b "cn=netadmins,ou=grupos,dc=lab,dc=local" member
# Dar de baja a un usuario: se borra en UN sitio y deja de funcionar en toda la red
$ sudo ip netns exec estacion ldapdelete -x -H ldap://10.0.20.1 -D "cn=admin,dc=lab,dc=local" -W "uid=luis,ou=usuarios,dc=lab,dc=local"

    5. Lección de seguridad: LDAP sin cifrar

    dc
    $ sudo ip netns exec dc tcpdump -i eth0 -n -A port 389

    Repite el ldapwhoami de ana: en la captura aparece ana123 en claro. Por eso en producción se usa LDAPS (TLS, puerto 636), StartTLS (ldapsearch -ZZ) o Kerberos, y Active Directory moderno rechaza los simple bind sin cifrar.

    Cómo se usa esto en una red real

    NecesidadSolución típica
    Iniciar sesión en Linux con usuarios del directorioSSSD + PAM + NSS (id ana funcionaría en todos los equipos)
    Que solo netadmins entre por SSH a los routersSSSD + AllowGroups netadmins en sshd
    Reglas de sudo centralizadasReglas sudoRole en LDAP leídas por SSSD
    Wi-Fi o VPN con usuario y contraseña de empresa802.1X / RADIUS (FreeRADIUS) consultando LDAP
    Inicio de sesión único (SSO)Kerberos: un ticket al iniciar sesión vale para todos los servicios
    Web corporativaLDAP directo, o SAML/OIDC (Keycloak) apoyado en el directorio

    No configuramos SSSD en el laboratorio a propósito: los namespaces comparten /etc y PAM con tu Arch, así que cambiaría cómo inicias sesión en tu propio equipo. Para practicarlo de verdad, usa una máquina virtual.

    Avanzado: un Active Directory real con Samba

    El paquete samba de Arch puede actuar como controlador de dominio AD compatible con clientes Windows. Todo queda dentro de /tmp/lab-samba gracias a --targetdir. Es un servicio grande: considéralo un experimento, puede requerir ajustes según la versión.

    host · con el namespace dc del laboratorio (para antes slapd con Ctrl+C)
    $ sudo pacman -S --needed samba
$ sudo ip netns exec dc samba-tool domain provision --realm=LAB.LOCAL --domain=LAB --server-role=dc --dns-backend=SAMBA_INTERNAL --use-rfc2307 --host-ip=10.0.20.1 --adminpass='Admin.Lab.2026' --targetdir=/tmp/lab-samba --option="interfaces=lo eth0" --option="bind interfaces only=yes"
# Arrancar el DC en primer plano
$ sudo ip netns exec dc samba -i -s /tmp/lab-samba/etc/smb.conf
    host · otra terminal
    # Usuarios y grupos al estilo AD
$ sudo ip netns exec dc samba-tool user create ana 'Ana.Lab.2026' -s /tmp/lab-samba/etc/smb.conf
$ sudo ip netns exec dc samba-tool group add NetAdmins -s /tmp/lab-samba/etc/smb.conf
$ sudo ip netns exec dc samba-tool group addmembers NetAdmins ana -s /tmp/lab-samba/etc/smb.conf
$ sudo ip netns exec dc samba-tool user list -s /tmp/lab-samba/etc/smb.conf
# Los registros SRV con los que los clientes encuentran el dominio
$ sudo ip netns exec estacion dig @10.0.20.1 _ldap._tcp.lab.local SRV
$ sudo ip netns exec estacion dig @10.0.20.1 _kerberos._tcp.lab.local SRV
# Consultar el directorio AD por LDAPS (certificado autofirmado de Samba)
$ sudo ip netns exec estacion env LDAPTLS_REQCERT=never ldapsearch -H ldaps://10.0.20.1 -x -D "ana@lab.local" -w 'Ana.Lab.2026' -b "dc=lab,dc=local" "(sAMAccountName=ana)" memberOf
# Recursos compartidos SMB del DC
$ sudo ip netns exec estacion smbclient -L //10.0.20.1 -U ana

    Limpieza: Ctrl+C en samba y sudo rm -r /tmp/lab-samba.

    P.7 Resumen: modelo de permisos en una red

    PreguntaMecanismoDónde se aplica
    ¿Quién eres?Autenticación: contraseña, clave SSH, certificado, Kerberossshd, LDAP bind, TLS
    ¿Qué puedes hacer?Autorización: grupos, sudoers, ACLsudo, AllowGroups, ACL de slapd
    ¿Qué has hecho?Auditoría: registrosjournalctl, logs de sshd y slapd
    ¿Desde dónde?Segmentación: cortafuegos, VLANiptables, bridge vlan
    ¿Con qué privilegio mínimo?Capabilities, comandos concretos en sudosetcap, Cmnd_Alias
